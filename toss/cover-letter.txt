저는 성능 병목과 장애를 직접 재현하고, 측정 결과를 바탕으로 구조를 개선해온 경험을 토대로 높은 트래픽과 장애 상황에서도 신뢰할 수 있는 서비스를 만드는 데 기여하고자 토스뱅크 Server Developer 인턴에 지원했습니다.

## 문제를 스스로 정의하고, 해결 방향을 고민하며, 결과를 개선해나간 과정

실제 운영 중인 GRADU 프로젝트에서는 랭킹 조회마다 반복되던 약 12만 건의 DB 집계를 조회 경로에서 제거해 p95를 98% 개선했습니다.
새로운 랭킹 기능을 도입한 뒤 실제 사용자 규모를 고려해 k6로 VU를 단계적으로 높이며 부하 테스트를 진행했습니다. 이 과정에서 목표였던 p95 800ms를 크게 초과하는 2.98초의 응답 시간을 발견했습니다. 단순히 요청이 많아져 느려졌다고 보기보다 원인을 좁히기 위해 Slow Query Log와 랭킹 조회 흐름을 분석했고, 조회할 때마다 약 12만 건의 데이터를 COUNT, GROUP BY, ORDER BY로 다시 집계하는 쿼리가 반복되고 있음을 확인했습니다.
처음에는 인덱스로 쿼리 비용을 낮추는 방법을 검토했습니다. 하지만 인덱스를 적용하더라도 랭킹 조회마다 동일한 집계를 반복하는 구조는 그대로 남았습니다. 그래서 병목의 문제를 조회 속도가 아니라 계산 시점에 있다고 정의했습니다. 랭킹은 자주 조회되지만 값은 과목 등록과 수정 시점에만 바뀐다는 점에 착안해 집계를 데이터 변경 시점으로 옮기고 Redis ZSET/HASH 기반 Write-time Aggregation을 적용했습니다. 그 결과 p95를 2.98초에서 48.24ms까지 낮추고 반복되던 DB 집계 쿼리도 제거했습니다.

## 경험하지 못한 규모에 직접 다가갔던 과정

Backend System Design Lab에서는 실제 대규모 트래픽을 경험하기 어려운 한계를 직접 부하와 장애를 재현하는 방식으로 보완하며, 시스템을 단일 구조에서 분산 환경으로 확장하는 과정을 실험했습니다.
URL Shortener에서는 애플리케이션을 2개로 확장하고 Nginx를 통해 요청을 분산했습니다. 단순히 인스턴스를 늘리는 데 그치지 않고 한쪽에 장애가 발생해도 서비스가 유지되는지 확인하기 위해 App을 직접 중단했고, 다른 인스턴스로 요청이 전환되며 446,850건의 요청에서 실패율 0%를 검증했습니다. Redis 역시 Fallback과 Circuit Breaker로 요청 경로를 보호한 뒤 Sentinel 기반 다중화로 확장했고, Master를 중단한 상황에서도 Replica가 자동 승격되며 938,870건의 요청을 실패 없이 처리했습니다.
구조가 분산되면서 기존에는 문제가 없던 ID 생성 방식도 다시 검토했습니다. 단일 App에서는 Sequence 방식으로 충분했지만, 여러 인스턴스가 독립적으로 요청을 처리하는 환경에 맞춰 각 App에 Node ID를 부여하는 Snowflake 방식으로 전환했습니다. 이 과정에서 Clock Rollback과 Node ID 충돌 가능성까지 함께 검토했고, 동일 조건에서 Sequence RPS 1,624 대비 Snowflake RPS 1,660을 기록해 기존과 유사한 성능을 유지하면서도 분산 환경에 맞는 ID 생성 구조를 검증했습니다.

토스뱅크는 통장, 예적금, 대출 등 일상과 맞닿은 금융 서비스를 24시간 제공하는 만큼 작은 지연이나 장애도 서비스의 안정성과 데이터 신뢰성에 영향을 줄 수 있다고 생각합니다.
저는 운영 서비스의 병목을 개선하고, 경험하지 못한 규모는 직접 부하와 장애를 재현해 검증하는 방식으로 서버 개발 역량을 넓혀왔습니다. 토스뱅크에서는 이러한 문제 해결 방식을 실제 금융 서비스의 트래픽과 장애 상황에 연결해 안정적인 요청 처리를 만드는 데 기여하고, 나아가 시스템의 한계를 지표로 판단하며 확장성과 가용성을 함께 설계할 수 있는 서버 개발자로 성장하겠습니다.
